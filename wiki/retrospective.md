## 🔥 Kapso Webhook Debugging — Full Post-Mortem

### The Bug
User sends "Hi" via WhatsApp → BioMed receives webhook (200 OK) → NO reply sent. Our direct tests worked perfectly. Real WhatsApp didn't.

### Root Cause
**Kapso v2 sends webhooks in format `{"message": {...}, "conversation": {...}, "phone_number_id": "..."}` — completely different from Meta's standard `{"entry": [{"changes": [{"value": {"messages": [...]}}]}]}` format.**

Our `extract_message_event()` only handled Meta format, direct format, and batch format. Kapso v2's format was never parsed. Messages arrived, returned `event=None`, and were silently treated as "status updates" (acknowledged but not processed).

### Why It Took 3 Hours

| # | Wrong Turn | Why It Happened |
|---|---|---|
| 1 | **Wrong API key** | Copied API key from WhatsApp config page instead of Kapso API Keys page. Same-looking tokens, different purpose. |
| 2 | **Duplicate webhooks** | Two webhooks pointed to same URL — race condition masked the real issue. |
| 3 | **Batch format assumption** | Assumed Kapso v2 = batch format. Wrote batch parser that never triggered for real messages. |
| 4 | **Silent log filtering** | Python `logger.info()` never appeared in Railway (WARNING+ only). Spent hours adding logs that were invisible. |
| 5 | **Testing wrong format** | Tested with Meta format and batch format — both worked. Never tested actual Kapso v2 format because we didn't know it. |
| 6 | **Dashboard vs webhook mismatch** | Kapso dashboard "raw_payload" shows Meta's internal event, NOT what Kapso sends to our webhook. We matched against the wrong format. |

### How We Finally Found It
1. Added `print()` with `flush=True` to webhook handler (bypasses logging filter)
2. User sent "Hi" → Railway log showed: `keys=['message', 'conversation', 'is_new_conversation', 'phone_number_id']`
3. Immediately recognized the Kapso v2 format
4. Added parser for `payload.get("message")` as first check in `extract_message_event()`
5. Fixed in 1 commit

### Preventing This In Future Kapso Projects

| Rule | Why |
|---|---|
| **Log the raw webhook payload first** | Before any parsing, `print(json.dumps(payload)[:500])`. Always. |
| **Check Kapso dashboard for `kind` and `payload_version`** | `kind: "kapso"` + `payload_version: "v2"` = different format. |
| **Never trust the dashboard "raw_payload"** | It shows Meta's internal event, not Kapso's transformed webhook payload. |
| **Test with the ACTUAL format first** | Simulate the exact payload Kapso sends before testing Meta/batch fallbacks. |
| **Use `print()` not `logger.info()` in webhook handlers** | Railway captures stdout. Python logging may not be configured. |
| **API key ≠ WhatsApp config token** | Kapso has separate "API Keys" (for REST API) and "WhatsApp Configuration" (for phone number setup). |

## Questions We Should Have Asked First

| # | Question | Why it matters |
|---|---|---|
| Q1 | **What's the manufacturer order intake format?** | We built the manufacturer template first, then had to rewrite it. Would have saved one iteration. |
| Q2 | **Is there a per-product margin or a flat rate?** | We defaulted to flat R70 then added per-product margin. Knowing this upfront would have simplified the schema. |
| Q3 | **Does BioMed pay FL before or after customer pays BioMed?** | Determines the two-POP model. We guessed right, but this is a critical business flow question. |
| Q4 | **What's the courier name and fee?** | Hardcoded "The Courier Guy, R150" then made configurable. Should have been config from day one. |
| Q5 | **Do customers reorder? What info is stored?** | Determined the "collect once, reuse" pattern. We built the full profile collection before knowing this. |
| Q6 | **How does FL confirm receipt — waybill, WhatsApp reply, email?** | Determines whether we need a waybill callback endpoint (future scope). |
| Q7 | **What happens when FL is out of stock?** | No handling for stock rejection. Order stays in limbo. |
| Q8 | **Are we deploying via CLI or GitHub?** | Wasted time on `railway up` timeouts when GitHub auto-deploy would have been cleaner from the start. |
| Q9 | **Is `APP_ENV=production` ready?** | Still `development`. Need MANUFACTURER_PHONE and APP_SECRET set first. |

## Architecture Decisions

| Decision | Rationale |
|---|---|
| Two-POP model (not auto-forward on customer POP) | BioMed must pay FL first. Auto-forward on customer POP would send without BioMed's payment proof. |
| Preview-then-confirm for manufacturer POP | Prevents accidental sends. Admin sees the message before it goes out. |
| `AUTO_FORWARD_TO_MANUFACTURER=true` toggle | Can disable automation without code change. Useful during testing or if FL changes their number. |
| In-memory rate limiter (not Redis) | Simpler for single-instance Railway deploy. Add Redis if scaling to multiple instances. |
| SQLite for local dev, Postgres for prod | Tests run 5x faster locally. `connection.py` abstraction makes this seamless. |
| GitHub auto-deploy over CLI | `git push` triggers Railway deploy. More reliable than `npx railway up` which times out. |
