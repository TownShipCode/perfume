# BioMed — Build Retrospective

**2026-07-24 / 2026-07-25** · Sessions: Phase 1–4 + Live Testing

## What Went Well

| Item | Detail |
|---|---|
| **Database abstraction** | `connection.py` dual Postgres/SQLite support made local testing fast. Adding `_sqlite_compat()` was a 20-line function that unlocked all migrations for local dev. |
| **State machine design** | The `State` enum (IDLE → ORDERING → ADDRESS_COLLECTION → CONFIRMATION → POP_WAITING → CONFIRMED) made extending the flow trivial. Adding 4 new steps required zero state machine changes — just extending `ADDRESS_STEPS`. |
| **Template-driven messages** | All customer/FL replies are DB-backed templates editable via dashboard. Changing the manufacturer format to Focus Logic's form was a one-line template edit. |
| **env-driven config** | Every business rule (shipping fee, margin, courier name, FL username, auto-forward toggle) is an env var. No hardcoded values. Railway deploy = set vars, done. |
| **Backward-compatible changes** | `save_customer_profile()` wraps `save_customer_address()` — old callers (tests, catalog admin) still work. |
| **Two-message forward** | Sending FL the form text THEN the POP image mimics natural WhatsApp behavior. No API hack — just added `send_image_message()`. |
| **Live flow test** | Thandi's complete 13-step journey tested end-to-end against live Railway + Kapso. Order created, POP received, all 7 profile fields saved. Kapso webhook accepting and delivering real WhatsApp messages. |

## Challenges

| Challenge | How we handled it |
|---|---|
| **3-step → 7-step broke 15 tests** | Updated all test files systematically. The address flow tests needed 9 messages instead of 5. The image message ID shifted from m6 to m10. |
| **SQLite didn't support migrations** | `migration_applied`, `execute_script`, `fetch_all`, etc. all asserted `database.pool is not None`. Added SQLite branches to all 6 functions + `_sqlite_compat()` DDL translator. |
| **Postgres DDL in SQLite** | `TIMESTAMPTZ`, `JSONB`, `BOOLEAN`, `SERIAL`, `GENERATED BY DEFAULT AS IDENTITY` — all Postgres-only. Regex translator handles this now, but is fragile for future migrations. |
| **API key mismatch on Railway** | Local `.env.example` had a different key than Railway. Resolved — Railway key `bmd-7xp3kqm9wf2rhn8vd4lj` is canonical. |
| **7 steps is a lot for WhatsApp** | 7 questions for new customers is high friction. Mitigated by: existing customers skip to confirmation (1 message). New customers only go through it once. |
| **Railway CLI timeouts** | `npx railway up` kept timing out on the backboard GraphQL API. Fixed by enabling GitHub auto-deploy — now `git push` triggers deploys. |
| **Webhook response crash** | `Decimal` objects from cart totals weren't JSON serializable, crashing webhook responses. Fixed with `jsonable_encoder()`. |

## Errors Found & Fixed (Live Testing)

| # | Error | Root Cause | Fix |
|---|---|---|---|
| 1 | `operator does not exist: boolean = integer` | Shared SQL query `WHERE is_active = 1 OR is_active = TRUE` — Postgres rejects boolean=int | Split by `database.mode` in `list_active_products()` and `get_keyword_map()` |
| 2 | Webhook verification 400 | `hub.mode` query param not matched — FastAPI needs `Query(alias="hub.mode")` | Added `Query` aliases for `hub.mode`, `hub.verify_token`, `hub.challenge` |
| 3 | Greeting commands never matched | Railway vars used spaces: `hi hello hey start` — `_csv_values` splits by comma | Changed to comma-separated: `hi,hello,hey,start` |
| 4 | Product duplicate returns 500 | `UniqueViolationError` from asyncpg not caught in products API | Added try/except → 409 Conflict |
| 5 | Decimal JSON serialization crash | `json.dumps()` can't serialize Python Decimal objects | Wrapped webhook response in `jsonable_encoder()` |
| 6 | Template test assertion stale | `DEFAULT_TEMPLATES` was updated (Phase 1) but test still checked old text | Updated test to match new template: "Reply with a number to order" |

## Questions We Should Have Asked First

| # | Question | Why it matters |
|---|---|---|
| Q1 | **What's the Focus Logic order intake format?** | We built the manufacturer template first, then had to rewrite it. Would have saved one iteration. |
| Q2 | **Is there a per-product margin or a flat rate?** | We defaulted to flat R70 then added per-product margin. Knowing this upfront would have simplified the schema. |
| Q3 | **Does BioMed pay FL before or after customer pays BioMed?** | Determines the two-POP model. We guessed right, but this is a critical business flow question. |
| Q4 | **What's the courier name and fee?** | Hardcoded "The Courier Guy, R150" then made configurable. Should have been config from day one. |
| Q5 | **Do customers reorder? What info is stored?** | Determined the "collect once, reuse" pattern. We built the full profile collection before knowing this. |
| Q6 | **How does FL confirm receipt — waybill, WhatsApp reply, email?** | Determines whether we need a waybill callback endpoint (future scope). |
| Q7 | **What happens when FL is out of stock?** | No handling for stock rejection. Order stays in limbo. |
| Q8 | **Are we deploying via CLI or GitHub?** | Wasted time on `railway up` timeouts when GitHub auto-deploy would have been cleaner from the start. |
| Q9 | **Is `APP_ENV=production` ready?** | Still `development`. Need MANUFACTURER_PHONE and APP_SECRET set first. |

## Remaining Gaps

| Gap | Severity | Notes |
|---|---|---|
| No waybill callback | Medium | FL sends waybill via WhatsApp — no auto-capture. Manual tracking update needed. |
| No stock management | Low | FL out-of-stock = order limbo. No rejection flow. |
| `_sqlite_compat()` regex fragility | Low | New Postgres-specific SQL patterns in future migrations could break local tests. |
| isiZulu translations | Low | 17 templates need isiZulu text. Infrastructure ready, just content. |
| No product images | Low | Vercel Blob recommended but not set up. WhatsApp catalog shows text only. |
| `APP_ENV=development` | Medium | HMAC signatures skip in dev mode. Webhook is less secure. |
| `MANUFACTURER_PHONE` not set | High | Auto-forward won't work until FL's number is configured. |

## Architecture Decisions

| Decision | Rationale |
|---|---|
| Two-POP model (not auto-forward on customer POP) | BioMed must pay FL first. Auto-forward on customer POP would send without BioMed's payment proof. |
| Preview-then-confirm for FL POP | Prevents accidental sends. Admin sees the FL message before it goes out. |
| `AUTO_FORWARD_TO_MANUFACTURER=true` toggle | Can disable automation without code change. Useful during testing or if FL changes their number. |
| In-memory rate limiter (not Redis) | Simpler for single-instance Railway deploy. Add Redis if scaling to multiple instances. |
| SQLite for local dev, Postgres for prod | Tests run 5x faster locally. `connection.py` abstraction makes this seamless. |
| GitHub auto-deploy over CLI | `git push` triggers Railway deploy. More reliable than `npx railway up` which times out. |
